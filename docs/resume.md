## 项目经历

### AI 全流程托管系统

**背景**：做 Agent 开发时最直观的痛点：AI 单环节辅助已经够强，但环节之间的衔接全靠人——需求到方案、方案到编码，每一步交接都要人工搬运与盯守，且每次交接都在重新理解背景、上下文层层衰减。单环节提效是加法，流程托管改变交付模式，价值量级不同；而本质做的是「流程托管」的通用能力，研发流程只是第一个打透的场景。据此构想以研发流程（需求 → 方案 → 编码 → 提测 → 部署 → 交付）为切入的流程级 AI 托管系统，架构不绑定单一场景，可组装生态内产品（审批平台、IM 等）适配其他行业。

**角色**：系统架构师 —— 产出全部需求决策与架构设计，主导技术评审，落地由团队执行。

**技术要点**：

- **原子能力层（生态根基）**：将审批、代码生成、方案生成等环节能力沉淀为标准化原子能力——每个原子有独立输入/输出契约、可独立验证、可跨场景复用、可被编排；场景不是硬编码的流程，而是从能力池中按需组装的产物。系统沉淀的原子越多，新场景的组装成本越低——能力的生产与复用形成复利，这是「生态」的根基
- **场景 = 原子能力编排**：环节序列、关卡规则、原子能力绑定三要素组合定义场景，新场景接入不动核心引擎（设计目标）；凡「流程 + 能力」可描述的场景皆可托管，如仓储出库：审批原子声明货品 → 传感器/终端设备验证原子，消除人工信息传递
- **关卡式管线设计**：流程拆解为需求/方案/编码/提测等环节，环节产出先经质量关卡，通过后才作为下一环节输入——把关点同时是环节间的上下文交接点，错误不会沿管线向下游传播
- **三层质量把关**：关键节点人工确认位 + AI 产出的自动校验/评审（lint、测试等）+ 校验不过的回退重试（含最大重试次数与升级人工的阶梯策略）——托管的信任基础；原子能力的独立可验证性让把关可以精准落在单个环节，而非整条链路
- **两阶段演进决策**：MVP 阶段基于现有 agent 快速验证流程闭环，稳定后切换自研编排引擎——避免 Day 1 自研深坑，也避免长期被现成方案的能力边界锁死
- **MCP 连接层**：原子能力对外统一通过 MCP 协议接入工具生态（见「内部系统 MCP 化」），托管系统不直接感知各内部系统细节
- **人机协同设计**：关卡即人机切换点——自动执行到关卡停下等确认；所有节点流转支持 AI 驱动与人工推进双模，托管不是黑盒自动驾驶，人可在任意节点接管推进
- **原子能力可观测**：各原子能力的执行状态与产出均有人工可观测渠道——AI 在做什么、结果如何，随时可查可监督，托管全程透明

**结果/状态**：完成完整架构设计与技术评审；关键环节已独立验证，处于环节串联与链路开发阶段。

### 内部系统 MCP 化

**背景**：团队 Agent 开发需要接入内部系统（审批、IM 等），但这些平台为人工操作设计，AI 无法直接调用；各项目为图快直接裸调 API——对接细节散落各处、重复封装、行为不一。作为托管系统的前置工程发起：托管系统按能力编排流程，需要一层面向 AI 的统一工具层支撑。

**角色**：发起（托管系统前置工程）、架构设计 & 核心实现。

**技术要点**：

- **按能力域划分 MCP Server**：托管平台按能力编排流程，MCP 工具层随之按能力域划分——两层同构，托管系统编排的能力即 MCP 暴露的能力，粒度一一对应
- **面向 AI 的能力转译**：将人工操作设计的内部平台能力封装为标准化 MCP 工具（统一输入/输出契约与错误语义），原平台无需改造，各项目由此告别裸调 API
- **工具层与 Agent 解耦**：Agent 侧只声明工具需求、不感知对接细节，新增内部系统接入对 Agent 代码零侵入；连接管理/鉴权/错误处理收敛到统一连接层，托管系统与团队各 Agent 项目共享
- **覆盖内部系统**：审批、IM、需求、代码、发布、自动化测试等平台——研发全链路打通，从需求到发布 AI 全程可触达

**结果/状态**：团队级在用，成为团队 Agent 开发的基础工具层。

### Agent 交互层优化

**背景**：公司 Agent 产品的前端交互层由我负责，交互体验直接决定用户对 Agent 的第一感知——但流式对话卡顿掉帧、Agent 调了什么工具用户一无所知、会话出问题无从回溯等交互问题都需要治理。

**角色**：独立设计与实现。

**技术要点**：

- **流式渲染性能治理**：高频 token 更新打满主线程、长对话历史越用越卡、富内容流式中反复重解析三类症状分别治理——时间窗口批量提交（token 攒帧再渲染，牺牲即时性换流畅）、视口分级渲染（可视区实时、视口外延迟/骨架降级）、富内容延迟升级（流式阶段纯文本、消息完成后再解析代码块/图表）
- **统一事件模型**：Agent 的思考、工具调用、工具结果、文本输出统一抽象为带类型的事件流，前端按事件类型分发渲染器——新增事件类型只加渲染器不改架构，渲染层对 Agent 能力扩展零改动
- **长连接可靠性**：断线检测与自动重连设计，保障对话流不因网络抖动中断丢失
- **工具调用可视化**：Agent 正在调什么工具、参数与结果如何，对用户实时可见
- **会话重放**：基于统一事件模型回放完整会话过程——出问题时可回到现场逐步回看 Agent 的每一步行为，定位问题不再靠猜

**结果/状态**：上线支撑团队 Agent 产品日常使用。

### 电商会场搭建系统

**背景**：电商大促会场页开发的双重痛点：运营每搭一场活动都要前端人工排期开发、上线慢；会场页楼层结构高度雷同、重复开发——需要「运营自助搭建提效 + 组件沉淀复用降本」双管齐下。

**角色**：全链路参与——搭建器、组件体系、渲染发布链路。

**技术要点**：

- **全 DSL 驱动架构**：整个搭建页由 DSL 驱动——所有交互编辑实际都是在改动 DSL 配置，渲染端统一消费 DSL，编辑态与渲染态共用同一份数据模型
- **楼层式搭建模式**：贴合电商会场竖屏分楼层的固有形态——添加楼层、排序调位完成页面骨架，楼层组件的配置项驱动组件行为，运营零代码完成会场搭建
- **渲染链路重构（CSR → BFF 预渲染 + CSR）**：纯 CSR 渲染遇到性能瓶颈（白屏时间等），主导重构为两阶段模式：BFF 预渲染时预请求注入数据（首屏直出、消除白屏等待），CSR 拉取最新数据重新渲染保证实时性——大促流量下首屏性能与数据新鲜度兼得
- **Agent 生成 DSL 驱动搭建**：DSL 驱动架构天然适配 Agent——Agent 直接生成 DSL 即完成页面搭建，运营配置之外新增 AI 搭建入口，前端资产成为 Agent 可操作的对象

**结果/状态**：支撑双十一、618、国庆、元旦、春节、品牌日等全量大促场景，整个事业群多条业务线日常使用。

### 商品模板编辑器（含自研预览引擎）

**背景**：跨境电商时期，运营创建/修改产品模板的核心工具，配套完全独立开发的自研预览引擎。

**角色**：独立设计与开发（预览引擎以 npm 私有包发布，供前台/编辑器/服务端渲染三端共用）。

**技术栈**：React18 · React-DnD · mobx · Ant Design · Three.js · Konva · jimp · lena.js · fontfaceObserver · TypeScript · Webpack5 / Vite · Firebase

**技术要点**：

- 拖拽画布交互体系：基于 React-DnD 实现组件拖拽、选中、图层面板，配合属性侧栏（mobx 状态管理）完成组件配置；支持分层渲染与整体渲染两种模式
- 组件体系与 Schema：组件配置导出为 JSON 格式的渲染信息，前台、编辑器、服务端共用同一 Schema，模板一次创建三端一致
- 2D/3D 双模预览：2D 基于 Konva 分层渲染与截图截取；3D 基于 Three.js，由中央控制器按产品配置统一调度，模型渲染与主体逻辑分离——新增模型不改主流程
- Sku 解析驱动配置：通过解析 Sku 生成产品配置与预设信息，对外暴露内部接口与钩子，支持模块与模型动态导入
- 渲染时序控制：Promise 并发加载图片/字体/材质，编排异步资源就绪与分层渲染的时序，保证预览一致性
- 用户层渲染优化：低像素模式快速生成预览图，缩短交互等待
- 服务端渲染打包：Webpack 输出 SSR bundle，Vite 支撑模型开发预览
- 3D 模型自制：Blender 完成基础建模与材质调整后接入 Three.js；3D 模式可直接导出场景图用于首页展示与推广
- 售后闭环：预览模式可直接下载裁剪图，覆盖用户下单填写错误需协助修改的售后场景

**结果/状态**：完整交付并支撑运营日常模板制作；预览引擎以 npm 私有包沉淀，三端复用。
